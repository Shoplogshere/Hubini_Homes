Hubini — WebSocket Protocol Flow

Cloud ↔ Device ↔ App communication spec  ·  Updated April 2026

Backend: https://hubini-homes.onrender.com

1. Who Connects to What

Everything connects to the cloud over a single WebSocket endpoint:

wss://hubini-homes.onrender.com/ws

REST API base:

https://hubini-homes.onrender.com/api/v1

Three types of clients can connect:

Client typeWhat it isFirst message after connect
AppMobile / web appauth|<jwt>
Device (node)Physical IoT devicemews|<dbId>
HubLocal IoT hubmewh|<dbId>
Heads up: The server sends nothing when a client first connects. The client always speaks first.

2. App Connection & Auth

Step 1 — App connects and authenticates

App
→
auth|<jwt>
Cloud
→
auth|<appId>
App
App sends: auth|eyJhbGciOiJIUzI1NiIsInR5cCI6... Cloud replies: auth|a3f9c2e17d4b8801fa20
The appId the cloud returns is this app session's identity. The app must save it and include it in every command it sends. It changes each new WS connection.

Alternative — get appId via HTTP

The appId is also included in the response when the app fetches its device list over HTTPS. Either way works — pick whichever fits the app flow better.

GET /api/v1/devices/client → returns devices + appId

3. Device / Hub Registration

Device registers

Device
→
mews|<dbId>
Cloud
→
registered|...
Device
Device sends: mews|42 Cloud replies: registered|42|free|free dbId userPlan devPlan

The device should store the plans it gets here. The cloud won't resend them in every command.

Hub registers

Same flow, just replace mews with mewh. Response is identical.

Activation window: After a device/hub is registered via the REST API, it has ~1000 seconds to connect and send mews/mewh. If it doesn't connect in time, the cloud auto-deletes it from the database.

4. Three-Way Command Flow (App → Cloud → Device → Back)

Every payload in this flow always starts with:
<cmd>|<devId>|<appId>|<todo>|<args...>
That leading structure is the contract — both sides can always parse who this is for and what to do.

Step 1 — App sends command

App
→
c_nd|...
Cloud
c_nd|42|a3f9c2e17d4b8801fa20|triga|R2|0 dbId appId todo switchId state

Step 2 — Cloud relays to device

Cloud swaps the dbId for the device's cloudId (the DEV_xxxx string) before forwarding:

Cloud
→
c_nd|...
Device
c_nd|DEV_abc123_f4e1|a3f9c2e17d4b8801fa20|triga|R2|0 cloudId appId todo switchId state
Device: you receive the appId here but it's not yours — it belongs to the app session that sent the command. Just echo it back unchanged in your response so the cloud knows where to route the reply.

Step 3 — Device responds

Device
→
r_nd|...
Cloud
→
r_nd|...
App
Device sends: r_nd|DEV_abc123_f4e1|a3f9c2e17d4b8801fa20|resptriga|R2|0|Off cloudId appId respTodo switchId state stateName

Cloud updates the device's last state in the DB, then forwards the exact same payload to the app session that matches the appId.

Todo / respTodo naming convention

todo (app → device)respTodo (device → app)Extra args
trigaresptrigaswitchId | state | stateName
anythingrespanythingwhatever the device needs to return
Pattern is always resp + todo. Simple and consistent on both sides.

5. HTTP-Originated Commands (no app WS session)

When a command comes from an HTTP request (not a WS app session), the cloud sets appId = -. The device still gets the same c_nd format. When it responds and the cloud sees appId = -, it broadcasts the state update to all of that user's connected app sessions instead of routing to one specific app.

c_nd|DEV_abc123_f4e1|-|triga|R2|0 ^ appId = - means HTTP origin, response broadcasts to all user app sessions

6. Device Ping / Pong (Heartbeat & Push)

The device sends ping every ~30 seconds to stay alive on the cloud and to check if the server has anything for it.

If nothing pending — cloud stays silent

Device
→
ping
Cloud
← no reply

Cloud still updates last_seen and keeps the device marked online — it just doesn't send anything back.

If server has queued data — cloud replies pong

Device
→
ping
Cloud
→
pong|...
Device
pong|DEV_abc123_f4e1|<cmd>|<data> devId what it is the actual data

Examples of queued pong payloads

ScenarioPayload
Booking queued (e.g. GhostAir)pong|DEV_xxxx|gair_b|<booking data>
User plan changedpong|DEV_xxxx|plan_change|free|pro
How the queue works: The cloud keeps a per-device queue. Whenever something needs to reach a device (booking, plan update, etc.), it gets added to that queue. On the next ping, the cloud drains the whole queue — one pong per item — then clears it. If multiple pings arrive before anything is queued, the cloud just stays silent each time.

8. Full Example — App Controls a Switch

1. App authenticates: App → Cloud : auth|eyJhbGci... Cloud → App : auth|a3f9c2e17d4b8801fa20 ← app saves this as its appId 2. App sends command to turn off switch R2 on device 42: App → Cloud : c_nd|42|a3f9c2e17d4b8801fa20|triga|R2|0 3. Cloud relays to device (swaps dbId → cloudId): Cloud → Device: c_nd|DEV_abc123_f4e1|a3f9c2e17d4b8801fa20|triga|R2|0 4. Device executes, responds: Device→ Cloud : r_nd|DEV_abc123_f4e1|a3f9c2e17d4b8801fa20|resptriga|R2|0|Off 5. Cloud updates DB state, routes response back to app: Cloud → App : r_nd|DEV_abc123_f4e1|a3f9c2e17d4b8801fa20|resptriga|R2|0|Off
